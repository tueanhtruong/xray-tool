# US-08.2 — Multi-project repository and pull controls

| Field      | Value                                             |
| ---------- | ------------------------------------------------- |
| Milestone  | M2 Read                                           |
| Depends on | US-08.1                                           |
| State      | tracked in [feature-list.json](feature-list.json) |

## User story

As a QA engineer, I want to switch among Jira projects while retaining their repository caches, and refresh all or part of a project from clear controls, so I can work across projects without losing local edits or waiting for unnecessary full pulls.

As an authorized user, I want the read-only repository cache for a Jira project to be reusable by other authorized users, while keeping each user's unsynced drafts private and independent.

## Context

The current workspace owns one selected project, its folder and test caches, and its Jira/Xray connections. Project replacement deletes the old cache. This story revises that single-project cache assumption: users may have separate workspaces and credentials, while authorized workspaces for the same Jira tenant/project refer to one shared remote cache. A user's active project must not be a mutable global project selection that changes another user's view or another browser tab's project context.

This story establishes the data and routing contract for US-09 drafts. Remote project data is shared; draft edits and their base versions are private to the editing user. Sharing a current remote snapshot must never change the version against which another user's draft is compared.

## Scope

**In**

_Project and cache ownership_

- Identify a Jira project by tenant identity plus Jira project ID. Use Atlassian `cloudId` where available, otherwise the normalized Jira `siteOrigin` used by API-token workspaces. Do not treat a numeric project ID, project key, or folder path alone as globally unique.
- Add a shared project record and workspace-to-project authorization/connection association. A workspace is associated only after that user's Jira project lookup and Xray access probe succeed. Shared cache existence is not authorization: all project reads and pulls must validate the requesting workspace's association.
- Move remote `Folder` and `TestCase` index rows to project ownership. Folder identity is `(project, path)`; remote test identity is `(project, Xray issueId)`, with project-scoped key uniqueness. Folder refresh timestamps and project metadata/status options are project-scoped as well.
- Preserve existing data during migration, including separating rows from different Jira tenants/projects that previously shared a workspace key. Keep `origin = IMPORT` tests private to their creator; never expose local/imported tests through the shared remote project cache.
- Keep project selection/context user-scoped and request-scoped. Selecting a project updates the current view/URL; every repository, detail, draft, and pull request identifies and authorizes its project. Two users and two browser tabs may operate on different projects without changing each other's context.
- Do not delete a project's cache when a user switches projects. Returning to a project shows its retained cache and last-refresh time; switching alone performs no Xray call.
- Scope remote pulls and their progress to the project. Serialize or safely coalesce pulls for the same project, while allowing pulls for different projects to proceed independently. A pull must not update another user's active project.

_Draft isolation and baselines_

- Drafts are private to a user and a testcase, including when several users edit the same shared testcase. One user's draft reads, writes, discard, and project-switch checks must not affect another user's draft.
- Capture an immutable base version with each user's draft when it is first created. It includes normalized field values needed for field-level conflict detection and the fingerprint/remote revision. A project refresh, another user's edit, or another user's sync must not silently replace that draft's base.
- On a remote deletion, retain a testcase as remotely deleted while any user has a draft; show it only in that user's draft/review context. Remove it from the live project index for users without a draft. Pulls never write to Jira/Xray or discard drafts.
- When the current user switches away from a project containing their drafts, show **Review drafts**, **Switch and keep drafts**, and **Cancel**. Review opens that user's drafts for the current project. Switching retains them unchanged and does not sync/discard; Cancel leaves the project unchanged. Draft counts and choices are never based on another user's drafts.

_Header and pull controls_

- Add a keyboard-accessible searchable project combobox to `AppHeader`. Reuse the existing Jira project search API and pagination; do not create a second search integration. Display project key/name and the current project, with loading, empty, error, and selection states.
- Add **Refresh folders** in the header. It refreshes only the selected project's folder tree and project-scoped folder timestamp; it does not fetch or mutate testcases/drafts.
- Place **Refresh all project tests** at the top of the folder sidebar. Before starting, confirm that the complete selected-project test index (and any folder data included by the pull contract) will be refreshed and may take time. Progress and completion/error messages identify the project and show fetched/total counts. The action remains read-only with respect to Jira/Xray.
- When a folder is selected, show **Refresh this folder** in the test-list area. First verify through the Xray API contract whether tests in the selected folder and descendants can be queried efficiently and whether tests moved into/out of the subtree or deleted remotely can be reconciled safely. Include descendants. If the API cannot provide enough information to reconcile stale entries without misleading results, do not expose a purported folder-only refresh; instead provide the full-project refresh path with accurate wording and record the limitation.
- A supported folder refresh upserts tests in the selected subtree and reconciles moved/deleted tests without deleting tests that belong elsewhere. It reports progress scoped to the project/folder and never writes to Xray.

**Out**

- Team roles, shared draft editing, draft merging, and organization-wide billing. Users may share the read-only cache but retain private drafts.
- Diff review and writing drafts back to Jira/Xray (US-16 through US-20). The **Review drafts** choice is a navigation to the current user's project draft list, not an implicit sync.
- Background/distributed job infrastructure for multi-instance deployments; retain the repository's documented single-instance deployment assumption, while ensuring same-process project-scoped pull coordination.
- Import/export behavior beyond ensuring imported/local tests remain private (US-13/14).

## Acceptance criteria

```gherkin
Feature: Multi-project repository and pull controls

  Scenario: Projects are namespaced by Jira tenant
    Given two Jira tenants have the same numeric project ID and folder path
    When both projects are indexed
    Then their folders and testcases are stored and queried independently

  Scenario: Authorized users reuse the same project cache
    Given two users have independently verified access to the same Jira tenant and project
    When one user refreshes the project and the other opens it
    Then both users see the same remote folders and testcase index
    And neither user's Jira or Xray credentials are shared
    And a workspace without verified access cannot read that project by guessing its ID

  Scenario: Users retain independent project context and drafts
    Given two users are viewing the same project and have each drafted a change to one testcase
    When either user edits, reviews, discards, or switches projects
    Then only that user's draft and project context change
    And each draft retains the remote base version captured for that user

  Scenario: Project context is independent across tabs
    Given two tabs are open for the same user
    When one tab selects project A and the other selects project B
    Then subsequent repository and pull requests in each tab remain scoped to its URL project

  Scenario: Switching projects retains caches and drafts
    Given project A has a retained cache and the current user has unsynced drafts in A
    When the user chooses project B and selects "Switch and keep drafts"
    Then project A's folders, testcases, and the user's drafts remain stored
    And project B becomes active only in the current view
    And no Jira/Xray write occurs
    When the user returns to A
    Then A's cached repository and that user's drafts are available

  Scenario: Review or cancel a project switch with drafts
    Given the current user has unsynced drafts in project A
    When the user chooses "Review drafts"
    Then the user's draft list for A opens without changing project context
    When the user instead chooses "Cancel"
    Then project A remains selected and no cache or draft changes

  Scenario: Header project search reuses Jira discovery
    Given the user has access to multiple Jira projects
    When the user searches by project key or name in the header combobox
    Then matching projects are shown with keyboard-operable loading, pagination, empty, and error states
    And selecting a result changes only the current view's project context

  Scenario: Refresh folders does not pull tests
    Given a selected project has a cached test index
    When the user activates "Refresh folders"
    Then only that project's folder tree and folder refresh time change
    And testcase rows and user drafts remain unchanged

  Scenario: Full project refresh is explicit and observable
    Given a selected project has a cached repository
    When the user activates "Refresh all project tests"
    Then a confirmation names the project and warns that the full index may take time
    And confirming refreshes the full project index and displays project-scoped progress
    And canceling makes no changes

  Scenario: Folder refresh is safe for the selected subtree
    Given Xray supports a verified query and reconciliation contract for a folder subtree
    When the user refreshes a selected folder
    Then tests in that folder and descendants are refreshed
    And moved and remotely deleted tests are reconciled without affecting other folders
    And user drafts and their base versions are unchanged
    Given Xray cannot satisfy that contract
    Then the UI does not claim to refresh only that folder and offers the full-project refresh instead

  Scenario: Remote deletion preserves only affected users' drafts
    Given a testcase is removed from Xray and one user has a draft for it
    When the project is refreshed
    Then the testcase and draft remain available in that user's draft context and are marked remotely deleted
    And the testcase is absent from other users' live repository lists
```

## Verification

1. Static: `pnpm check`
2. Runtime: `pnpm test:int tests/integration/project-selection.test.ts`, `pnpm test:int tests/integration/project-cache.test.ts`, and pull/folder integration coverage for tenant isolation, authorization, project-scoped concurrency, migration preservation, draft isolation, and remote deletion.
3. End-to-end: `pnpm test:e2e e2e/us-08-2-multi-project-repository.spec.ts`
4. Xray contract: opt-in `pnpm test:live` against the configured sandbox to verify folder-scoped query and moved/deleted testcase reconciliation before enabling **Refresh this folder**.
